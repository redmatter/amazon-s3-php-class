A call would arrive into the PBX over SIP and RTP. Once the set policies are applied and the call get routed to appropriate destination device / number. As part of one of these policies, there could be a call-recording policy, which would setup and trigger call recording. When such policies are set, the switch software would start spooling voice data into a WAV file on the local disk.

When the call finishes, the WAV file is finalised and kept ready for the archiving process, to pick up. It would also generate the Call Detail Record (CDR) in XML format, and is dumped into a folder location monitored by the same archiving process. The archiving process is known as CollectD, as it is the one that collects various data for archiving. When a CDR picked up by CollectD, it inspects the CDR for any recordings that were setup during the progress of the call. CDR would also have information relating to the archiving policy to be applied, which is collected by CollectD as metadata. The identified recordings and metadata are added the queue of items to be sent to archiving service.

CollectD has the responsibility to collect any item to be archived, along with any meta data (required to enforce a policy and for making it available in searches) and send them off to the central archiving server. This data is sent over TCP using a custom file transfer protocol, with built-in data integrity checks. Once the archiving server (ArchiveD) receives and makes sure that it has received data with no corruption (verifies MD5), it acknowledges to CollectD, so that CollectD can relinquish the responsibility.

ArchiveD assumes responsibility and it adds the object into a queue, which is backed by database (so that it can recover from any failures). At this point, if one of files received is a CDR, a seperate local copy is created, which then is handed over to the CDR & Task processing system called CDR-Munch. The ArchiveD would "whisper" the path of the file to distiller process, which then runs some XML transformation algorithm on the CDR to normalise the CDR and also to identify any extra tasks to be performed on the CDR (like emails to be sent or SMS notifications or billing information). One of these tasks is the Log feeder, which analyses CDRs associated with a call to identify various call scenarios (transfers, etc) and make them available for searches etc ( which acts as the entry point into the archived call recordings as well).

ArchiveD would also continue on with the archiving process; first of all, it gets details about the policy applied on the recording, which then identifies the storage-endpoint to which the file is to be saved. It also makes sure there is a valid policy set before any further processing is performed (which are resource intensive). Then the file is compressed and then encryoted with individual keys (per organisation), with appropriate intermediate checksums to identify corruption if any.

Once the compressed and encrypted file is created, it is stored to the configured storage endpoint, which is an Amazon S3 Bucket, over HTTPS. When we make the request, the MD5 of the file is specified, so that Amazon will verify the payload when it receives the file and comeback with an error if a corruption is detected. Once stored, a retention record per file is created in the database (Retention DB), which then is used to control access to the item and also to feed the purge mechanism.

When a user attempts to access a recording, the access comes in via the WEB interface, which then proxies in via the the API. The API would verify the user to be authenticated ( unless unrestricted access is ON on the policy enforced for the object being accessed ). If the user is authenticated, the policy identified from the object's retention record is used to validate the user against the ACL. If the policy mandates a reason for access to be asked to teh user, the API will deny access till such a reason is provided and an audit log is generated. Other wise, a simpler form if audit log is generated for the particular access, and the audit-log identifier is used to forward the access request to archiving server. The archiving server will double check the audit-id. Once verified, it will use the endpoint identified tagged against the retention-record to access the storage endpoint ( configuration from API). Once the compressed-and-encrypted file is downloaded from the endpoint, it needs to be first of all decrypted. If the access was authenticated, it will use the user's OrgID to work out the decryption key to use. Other wise if the user is unauthenticated, it will allow the access after double-checking the unrestricted access flag on the policy ( and it uses the OrgID from the object identifier ). The key is used to decrypt the file. The decrypted file is then check-summed and verified against the checksum present in the file-header to make sure there are no corruptions. The the file is decompressed and streamed back to the browser ( via the API and the WEB server ).
